Reed-solomon-simd fused eight-output multiplication: upstream handoff

Purpose
Add a reusable GF(2^16) multiply/XOR primitive to the existing Engine abstraction. Lumina RLC computes eight field components from the same input column. Its existing-primitive prototype copies each column eight times, invokes Engine::mul eight times, and performs eight separate XOR passes. The candidate loads each source block and decomposes its nibbles once, then accumulates eight products directly into the eight destinations. This is an additive low-level engine operation; RS encoding/decoding algorithms and public codec APIs are unchanged by the dependency patch.

Proposed API
    fn mul_add8(
        &self,
        input: &[[u8; 64]],
        outputs: &mut [&mut [[u8; 64]]; 8],
        coefficients: &[GfElement; 8],
    )
For each component c, block b and GF16 position j: outputs[c][b][j] ^= input[b][j] * coefficients[c]. The notation describes field elements; actual blocks use the existing Leopard layout: 32 low bytes followed by 32 high bytes.
Coefficients are raw field values, not logarithms. Zero must leave its destination unchanged. Never pass the log-table zero sentinel to Engine::mul as though it represented a zero multiplier. The API accepts empty input and preserves its input. Every output must have the same block count as input, including outputs with a zero coefficient; mismatches panic. No atomicity on a failing length check is promised. Rust mutable references enforce disjoint output ownership. The provided method remains object-safe and adds no required method to third-party Engine implementations.
API and portable fallback: src/engine.rs:154. The default implementation skips zero coefficients, uses a stack 64-byte temporary, calls the selected engine's existing mul, and XORs the result. This maintains support for all current engines without implementing every SIMD backend at once. It is a correctness fallback; its performance has not been measured on non-AVX2 machines.
Dispatch: src/engine/engine_default.rs:93 (locate mul_add8 if rebasing changes line numbers). DefaultEngine must forward the new method to its boxed engine; relying on the trait default here would bypass the AVX2 override.
AVX2 entry: src/engine/engine_avx2.rs:77. It explicitly checks AVX2 before entering target_feature code; do not assume every caller obtained Avx2 through DefaultEngine. The existing Avx2::new constructor alone does not enforce CPU support.
AVX2 kernel: src/engine/engine_avx2.rs:523. Each block loads two unaligned 256-bit halves, derives four nibble vectors, then uses the existing multiply128 lookup tables for each nonzero coefficient. Broadcast/shuffle/XOR operations update both destination halves directly. Length checks precede accesses, each vector access stays within a 64-byte block, and no alignment beyond u8 is assumed. No instructions above AVX2 are required by this kernel.

The fork reduces isolated RLC time by about 20% relative to existing Engine::mul batching, and by about 74% relative to the scalar baseline. The ~3.8x scalar comparison is not the incremental benefit of adding this primitive: most of that improvement comes from batching with existing SIMD support. Full encoding improves about 4.35% at one worker relative to existing-primitive batching. Small multithreaded differences between fused and existing-primitive variants are within observed noise. Private and fork fusion are comparable; no convincing speed argument favors owning the kernel in Lumina.
Baseline peak-to-peak noise divided by median was 0.58% / 12.36% for isolated RLC at 1/16 workers and 0.49% / 12.42% / 33.90% for full encoding at 1/16/32. Quick-mode samples do not establish small differences. The final prototype's 16-worker process samples were 14.408, 9.116 and 9.159 ms; all samples must remain visible when interpreting its median.
RLC timing excludes coefficient derivation/cloning but includes batching setup, transpose, allocation, multiplication, reduction and output creation. This is a caller workload benchmark, not a primitive-only microbenchmark. Stock assembly confirms the fused path removes per-component source copies and separate XOR passes. Rust perf samples: 40.42% fused AVX2 kernel, 56.49% surrounding batch closure, including transpose. Go executes AVX-512/GFNI on this CPU and measures about 81.35/5.61 ms; that is not an AVX2-to-AVX2 comparison.

Before submitting upstream
Recheck the upstream base and Engine API; these observations concern 3.1.0. Apply the included patch on a branch based on the intended upstream revision and rerun the dependency suite. Keep the library PR limited to the engine primitive, dispatch, tests and benchmark evidence; the Lumina transpose and worker scheduler belong in the caller.
Audit existing engine benchmarks and add the smallest benchmark needed to compare eight copy/mul/XOR passes with mul_add8 at equal input/output sizes. Include tiny and larger block counts, nonzero prefilled outputs, mixed/zero coefficients, allocation boundaries and the portable fallback. The current ~20% figure measures the complete RLC helper, not primitive-only throughput. Recheck full RLC integration after any kernel or dispatch change.
Review whether the fixed eight-output name/signature fits the library API. Eight corresponds to Lumina's GF128 components; do not introduce a generic abstraction or extra optimized backends without a measured need. Preserve raw-zero semantics, object safety, default forwarding, non-AVX2 fallback, bounds and CPU-feature checks.
Move the new AVX2 impl above the existing TESTS divider if preparing a polished upstream patch; its current location below that divider is cosmetic. Disassembly also shows per-block LUT pointer copying from zip(luts) and repeated broadcasts. Optimizing those is unmeasured follow-up work; do not silently claim extra gains from changing them.
Rust 1.82 compatibility must be preserved unless maintainers choose otherwise. Keep intrinsics inside explicit unsafe blocks with documented CPU, bounds and alignment invariants. A backport to the currently used 3.1.0 base is already demonstrated; backports to other revisions need their own compile/tests.
Suggested upstream title: Add an eight-output GF16 multiply-accumulate engine operation.
Suggested summary: Add Engine::mul_add8 with a portable provided implementation, DefaultEngine forwarding and an AVX2 override. Reuse each source load and nibble decomposition across eight independently weighted XOR destinations. Lumina's batched RLC workload measures about 20% lower isolated latency than composing the existing in-place multiplication primitive; correctness tests cover zeros, accumulation, layout and available engines.
